# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файлы из `migrations/` монтируются в `docker-entrypoint-initdb.d` и применяются только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

### Маршруты

| Метод  | Путь                    | Описание                              |
|--------|-------------------------|---------------------------------------|
| POST   | /api/v1/tasks           | Создать задачу                        |
| GET    | /api/v1/tasks           | Список всех задач                     |
| GET    | /api/v1/tasks/schedule  | Задачи, запланированные на дату       |
| GET    | /api/v1/tasks/{id}      | Получить задачу по ID                 |
| PUT    | /api/v1/tasks/{id}      | Обновить задачу                       |
| DELETE | /api/v1/tasks/{id}      | Удалить задачу                        |

## Функциональность периодичности

### Концепция

Задача может быть **разовой** (без поля `recurrence`) или **периодической** (с заполненным `recurrence`).

Периодическая задача — это шаблон расписания. Чтобы узнать, какие задачи назначены на конкретный день, используется эндпоинт `GET /api/v1/tasks/schedule?date=YYYY-MM-DD`.

### Типы периодичности

#### `daily` — каждые N дней

```json
{
  "recurrence": {
    "type": "daily",
    "every_n_days": 1,
    "start_date": "2024-01-01"
  }
}
```

- `every_n_days` — обязательное поле, >= 1. Например, `1` — каждый день, `7` — раз в неделю.
- `start_date` — необязательное поле (YYYY-MM-DD). Дата первого вхождения. По умолчанию — дата создания задачи.

#### `monthly` — в определённое число каждого месяца

```json
{
  "recurrence": {
    "type": "monthly",
    "day_of_month": 15
  }
}
```

- `day_of_month` — число месяца от 1 до 30. Если в месяце нет такого числа (например, 30 февраля), задача в этом месяце не появляется.

#### `specific_dates` — конкретные даты

```json
{
  "recurrence": {
    "type": "specific_dates",
    "dates": ["2024-01-15", "2024-02-20", "2024-03-10"]
  }
}
```

- `dates` — непустой список дат в формате YYYY-MM-DD.

#### `even_odd` — чётные или нечётные числа месяца

```json
{
  "recurrence": {
    "type": "even_odd",
    "parity": "even"
  }
}
```

- `parity` — `"even"` (чётные числа: 2, 4, 6, ...) или `"odd"` (нечётные: 1, 3, 5, ...).

---

### Эндпоинт расписания

```
GET /api/v1/tasks/schedule?date=2024-01-15
```

Возвращает все задачи, у которых настройки периодичности соответствуют указанной дате.

- Параметр `date` — необязательный, формат YYYY-MM-DD. По умолчанию — сегодня (UTC).
- Задачи без `recurrence` в результат не включаются.

**Пример ответа:**

```json
[
  {
    "id": 1,
    "title": "Ежедневный обзвон пациентов",
    "description": "",
    "status": "new",
    "recurrence": {
      "type": "daily",
      "every_n_days": 1,
      "start_date": "2024-01-01"
    },
    "created_at": "2024-01-01T10:00:00Z",
    "updated_at": "2024-01-01T10:00:00Z"
  }
]
```

## Принятые архитектурные решения и допущения

### 1. Шаблон расписания, а не экземпляры задач

Задача с периодичностью является **шаблоном**, а не автоматически порождает отдельные записи в БД на каждую дату. Вместо этого логика "попадает ли задача на дату X" вычисляется в сервисном слое при запросе `/schedule`.

**Почему:** Генерация экземпляров требует фонового планировщика, управления жизненным циклом экземпляров (удаление устаревших, обработка изменений шаблона), что значительно усложняет систему. Для целей трекера врачей достаточно спросить "что мне нужно сделать сегодня?" — именно это и решает `/schedule`.

### 2. `day_of_month` ограничен 1–30, а не 1–31

Дни 29, 30, 31 существуют не во всех месяцах. Ограничение до 30 позволяет избежать путаницы с 31-м (не существует в 6 из 12 месяцев). Если нужен последний день месяца, это отдельный тип, который можно добавить позже. Дата 30 февраля просто не совпадёт ни с одним реальным днём и задача в феврале не появится.

### 3. Фильтрация в памяти (Go), не в SQL

`ListByDate` загружает все задачи и фильтрует их в Go. Для медицинского трекера с сотнями задач это допустимо. При необходимости масштабирования фильтрацию можно перенести в JSONB-запросы PostgreSQL (`recurrence->>'type' = 'monthly'` и т. д.).

### 4. `start_date` для `daily` задаётся по умолчанию датой создания

Если пользователь не указал `start_date` для типа `daily`, он автоматически устанавливается равным дате создания задачи (UTC). Это интуитивно: "начиная с сегодня, каждые N дней".

### 5. Обновление задачи полностью заменяет `recurrence`

PUT-запрос заменяет поле `recurrence` целиком. Чтобы удалить периодичность, нужно передать `"recurrence": null`. Чтобы сохранить её без изменений — передать текущее значение.

### 6. Миграции применяются через `docker-entrypoint-initdb.d`

Файлы `0001_create_tasks.up.sql` и `0002_add_recurrence.up.sql` монтируются в папку, которую PostgreSQL выполняет только при инициализации пустой базы. При обновлении нужно пересоздать volume (`docker compose down -v`).
